How SLA compliance is measured — and what happens if we miss

We measure, we publish, and we downgrade honestly — never silently.
  1. Measured: every ticket is logged with its unit, tier, received time, acknowledge time, response time, and resolve/escalate time. Per unit × tier: % acknowledged within target, % substantively responded within target, % resolved-or-escalated within target. Target: ≥90% on all three.
  2. Published: the rolling 30-day compliance log is public at sla-compliance.html — the full ticket-level table, not a summary number. Day 1 starts empty with "measurement begins 2026-09-23" and is never backfilled: no ticket is entered for a day when logging was not live.
  3. Honest downgrade, never silent: if any unit × tier misses its target on >20% of tickets over a 30-day window, the published target is downgraded to what we actually achieved — the change is dated, announced in the log, and the old target is kept visible as history. What we promise is what we can keep.
  4. Kill rule: 30 days with >20% of tickets missing SLA → the published target is honestly downgraded that same week. Misses are never deleted and never re-labeled.

Escalation path

  1. Triage first: answer from the KB (index.html Q1–Q10, RB-01..RB-12) → reproduce → only then escalate.
  2. Content/KB issue → CWI_Guide.
  3. Monitoring/pipeline anomaly → CWI_Watch.
  4. Engineering authority (deploys, gates, CTO calls) → KingCode — deploy gate owner.
  5. Anything naming Black personally, wallets, credentials, spending, paid accounts, or security → Black, same day, his decision — never agent-acted.

Hard lines (never relaxed): no spending; no wallet signing; no credentials handled; nothing under Black's personal name; never promise fixes, dates, or payouts — only state what is verified.
